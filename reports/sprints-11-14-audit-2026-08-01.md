## 1. Executive summary

Verdict: **Not production ready**.

The repository contains substantial, connected implementations for all four sprints. This is not merely scaffolding: the Tool Executor is shared by SDK, native, and MCP tools; tenant fields and permission checks are widespread; real API clients back the new pages; 32 focused backend tests pass; the frontend production bundle builds; and unauthenticated live API requests are rejected.

It nevertheless falls materially short of the supplied specifications and of a production release bar. The most serious issue is a plaintext production database credential committed in `backend/app/database/postgres.py:17-19`; a failing test emitted the credential-bearing DSN into its traceback. That credential must be presumed compromised and rotated. The complete backend suite has four failures, lint and type checking fail, a clean SQLite migration chain fails, there is no CI configuration, browser-level authenticated workflows could not be verified, and several integrations presented as enterprise capabilities are local/fake implementations.

Critical blockers:

## 2. Architecture map and inventory

```text
React 19 / React Router / TanStack Query
  -> Axios API services + Cognito bearer token
  -> FastAPI routes (/api/v1)
     -> Cognito JWT dependency -> ExecutionContext
     -> Tool Registry (process-global Python objects)
     -> Tool Executor (schema, permission, policy, timeout, retry, redaction)
        -> Sprint 11 adapters / Sprint 12 native tools / Sprint 13 MCP adapter
        -> SQLAlchemy ToolExecution
     -> Sprint 14 discovery engine
        -> local feature-hash embedding -> JSON vectors -> in-process ranking
        -> marketplace profiles + assignments + policy evaluator
  -> PostgreSQL target / SQLite tests / Alembic
```

Backend: Python 3.14 environment, FastAPI 0.139, SQLAlchemy 2.0, Alembic, Pydantic, Cognito JWT verification, Prometheus metrics. `backend/app/main.py` is the entry point. New modules are under `tool_sdk`, `mcp_integration`, and `tool_discovery`; routes are in `api/tools.py`, `api/native_tools.py`, `api/mcp.py`, and `api/tool_discovery.py`. There is no job queue, distributed cache, analytics service, or dedicated repository layer for these sprints. Registry, executor, MCP manager, OAuth state, embedding cache, and discovery limiter are process globals.

Frontend: React 19, Vite 8, React Router, TanStack Query, Axios, MUI/lucide, and CSS. Routes exist for catalog/details/integrations/executions, native tools/workspaces, MCP list/create/details, discovery, marketplace, governance, and analytics (`frontend/src/app/router.jsx:149-161`). Loading/error/empty states exist unevenly. No application-wide error boundary was found. Sprint 11–14 frontend coverage is four mocked-service component tests across two pages.

Database: PostgreSQL is intended; SQLite is used by focused tests. The four sprint migrations form a linear chain `d7e9... -> e8f0... -> f9a1... -> a0b2...`. Tables cover definitions/executions/integrations, native files/connections/notifications, MCP servers/capabilities/syncs, and discovery/index/marketplace/assignments/policies/events/feedback. Tenant columns are present, but foreign keys and several uniqueness constraints are absent.

Infrastructure: a Postgres-only root `docker-compose.yml` and backend Dockerfiles exist. The root README is one sentence and the frontend README remains the Vite template. No `.github` CI workflow was found. `.env.example` documents many sprint settings, but a second hard-coded database module bypasses configuration.

## 4. Principal findings by sprint

### Sprint 11 — Tool SDK

The immutable metadata/contract, deterministic versioned registry, schema validation, permission checks, timeout/retry behavior, idempotency lookup, redaction, normalized envelopes, execution persistence, API catalog, and agent bridge are real and focused-test verified (`backend/app/tool_sdk/registry.py:14-92`, `executor.py:38-281`). The executor is reused by later sprints.

Gaps: `ToolRegistry._lock` is never used and mutation is synchronous (`registry.py:19-64`); catalog synchronization hard-codes tenant `default` (`service.py:14-50`); registry/executor are process globals (`service.py:9-11`); execution persistence doubles as audit rather than producing immutable `AuditLog` events; integrations are adapters awaiting credentials; and UI component tests cover only the catalog. Categories/providers/version listing do not filter by caller permission (`api/tools.py:119-134`), creating an inventory side channel for any authenticated user.

### Sprint 12 — Native enterprise tools

File upload, extraction, read/search/summarize, read-only SQL parsing, SSRF protections, notification approval rows, tenant filters, and common executor routing are implemented. Eight formats have actual parsers (`native_tools.py:40-130`), SQL is parsed with sqlglot and table allowlists (`:323-357`), and REST blocks private networks and redirects (`:422-543`).

The file scanner is only a literal EICAR substring check and processing is synchronous/in-memory (`:153-223`); local files are unencrypted by this application. Search is a bounded substring scan, not an indexed enterprise content search (`:267-292`). Database URLs and REST tokens resolve through dynamically named environment variables, not the persisted secret-reference abstraction (`:400-403`, `:512-513`). Email and Teams never contact providers: rows are marked sent and given fabricated IDs (`:603-623`); approval similarly changes state and fabricates an ID (`api/native_tools.py:341-367`). The Native Tools list hard-codes Enabled/version/risk, and its search input has no state or filtering (`frontend/src/pages/native/NativeToolsPage.jsx`).

### Sprint 13 — MCP integration

The official `mcp==1.28.1` dependency is pinned. Streamable HTTP and legacy SSE are implemented using the official client (`mcp_integration/client.py:8-12,43-86`). HTTPS/host/DNS controls, auth headers, bounded responses, tool/resource/template/prompt discovery, fingerprint review, approval-before-enable, and adaptation into the existing executor are present. OAuth uses PKCE and one-time state (`oauth.py:15-105`).

Connections are created and torn down on every operation, so there is no connection reuse, idle cleanup, reconnect strategy, or token refresh (`client.py:140-160`). Semaphore and OAuth state are process-local. OAuth exchanges a code but deliberately discards both tokens without implementing the promised secret-store handoff (`oauth.py:99-105`). The declared standards-compliant FastMCP provider is never started by tests; the integration tests inject `FakeClient` directly (`tests/test_mcp_integration.py:15-116`), so transport/protocol interoperability is not fake-server tested. The administration UI lacks edit/delete configuration, complete OAuth fields/flow, capability counts, and rich resource/prompt testing. Live MCP verification is blocked by credentials/endpoints.

### Sprint 14 — discovery and governance

The implementation extends the existing registry/executor. It persists index/profile/assignment/policy/event/feedback data, applies deterministic permission/policy/status/environment/classification/risk/cost filters, records anonymized rejection aggregates, exposes a broad API, and provides real API-backed discovery/marketplace/governance/analytics pages. Explicit deny and execution-time rechecks are implemented (`governance.py:41-147`, `executor.py:54-89`).

The “semantic” provider is signed feature hashing over token strings, not a semantic embedding model (`embedding.py:20-48`). All JSON vectors are loaded and scanned in Python (`engine.py:87-95,150`); no pgvector implementation exists. Indexing always selects the first limited batch without a cursor, so catalogs over 500 tools can never be fully rebuilt (`indexing.py:47-53`). The cache and rate limiter are unbounded/process-local (`embedding.py:25-42`, `rate_limit.py:9-28`). Search-document sanitization removes control characters and secret-named fields but does not defend against instruction/prompt injection in untrusted MCP descriptions (`indexing.py:12-33`).

The discovery loop performs per-candidate marketplace and execution queries, producing N+1 behavior (`engine.py:95-149`). Assignment `action` and optional `tool_version` fields are not evaluated (`governance.py:100-106`). Policy matching supports only nine fields and four operators; time windows, cost, roles/groups, tool version, and invalid-condition rejection are incomplete (`governance.py:11-38`). Low confidence returns a flag but has no durable clarification/review workflow. Approval is a boolean in execution context, with no request, approver, expiry, or resume record. `multi_tool` only returns multiple candidates and never orchestrates them (`engine.py:233-240`).

Marketplace tabs are inert buttons and assignments/governance actions are not wired (`frontend/src/pages/discovery/MarketplacePage.jsx`). Analytics exposes only a small subset of the mockup. Discovery simulation cannot select a simulated identity/role/group. The five-case benchmark passes but does not measure cross-tenant leakage—the value is hard-coded to zero—and lacks top-3, no-match, disabled/unhealthy/high-risk, latency, and cost thresholds (`backend/tests/test_discovery_benchmark.py`).

## 9. Security report

### P0 — Critical

**SEC-001: committed production database credential.** `backend/app/database/postgres.py:17-19` contains a full RDS DSN with username and password and is tracked by Git. Reproduction: `git grep -n 'postgresql://' backend/app/database/postgres.py`. A failed connection test prints the decoded password in exception parameters. Impact: database compromise and persistent secret exposure in source history/logs. Rotate the credential immediately, revoke it, remove it from code/history using an approved incident process, and use the central settings/secret manager. Do not merely delete the current line.

### P1 — High

**SEC-002: authenticated inventory leakage.** Category/provider/version endpoints return registry inventory without filtering caller permissions (`backend/app/api/tools.py:119-134`). This can reveal sensitive tool/provider names.

**SEC-003: unsafe error reflection in authentication.** `get_current_user` returns `str(ex)` to clients (`backend/app/auth/dependencies.py:18-25`), potentially exposing verifier/configuration internals.

**SEC-004: secret-reference validation is not a secret store.** Native connections accept arbitrary `secret_reference` strings but runtime reads separately named environment variables; MCP only supports `env://`. OAuth token handoff is absent. Operational users may believe credentials are securely stored when they are not.

**SEC-005: no durable approval evidence.** REST writes and Sprint 14 policy decisions rely on permissions/context flags, while notification approval only mutates a row. There is no immutable approver identity, reason, expiry, separation-of-duties, or replay-safe approval token.

### P2 — Medium

- MCP OAuth state, connection concurrency, discovery rate limits, and embedding cache are process-local; multi-worker deployment weakens consistency and rate limits.
- MCP/REST DNS validation occurs before connection and is still susceptible to DNS rebinding without transport-level pinning.
- Untrusted MCP descriptions enter discovery documents without prompt-injection neutralization.
- Native file scanning is a signature demo, not production malware/DLP scanning; files are stored unencrypted by the app.
- No CSRF concern was demonstrated for bearer-token APIs, but browser token storage/session controls could not be inspected in an authenticated session.
- Audit rows store sanitized execution inputs/outputs, but there is no immutable audit sink or retention/tamper control.

### P3 — Low

- Blind exception handlers hide cleanup/synchronization failures.
- Several UI controls lack accessible names and keyboard behavior.

## 12. Performance and reliability

- Discovery does full JSON-vector scans and per-candidate database queries; latency grows roughly with tool count plus N+1 queries.
- Index rebuild can permanently omit tools after the first 500; no background job/retry/resume exists.
- Analytics loads operational rows and performs per-tool queries; no rollups/cache/materialization.
- File upload reads the full file, base64-expands it, writes it, and extracts it in one async request using blocking libraries.
- Database execution uses synchronous SQLAlchemy inside an async tool and loads all rows after limit enforcement.
- Tool retries are bounded, exponential, and jittered; unknown exceptions are not retried.
- Notification idempotency has a database uniqueness constraint, but delivery is not real and approval/delivery atomicity is untested.
- MCP concurrency is bounded per process but every operation reconnects; no pooling/keepalive/refresh/recovery.
- REST/MCP timeouts and response sizes are bounded; database statement timeout is not explicitly set.
- Registry mutation is not protected by its declared lock; multi-worker state can diverge from database state.
- Graceful shutdown of long-running tool calls/MCP sessions is not specifically tested.

## 14. Final verdict

**Not production ready.**

The work is a meaningful prototype/alpha foundation, with especially solid reuse of the Sprint 11 execution path. It cannot honestly be called complete or production-ready while a live credential is committed, the repository test/static/migration gates fail, enterprise integrations are unverified or simulated, approval/governance workflows are incomplete, discovery does not scale, and authenticated end-to-end behavior has not been demonstrated.
